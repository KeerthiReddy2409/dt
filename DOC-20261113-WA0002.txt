Description
1. DevOps
DevOps is a combination of Development (Dev) and Operations (Ops). It is a software development approach that focuses on collaboration, automation, continuous integration, continuous delivery, and continuous monitoring.
DevOps helps organizations develop, test, and deliver software faster, more reliably, and efficiently.
2. DevOps Lifecycle
The DevOps lifecycle consists of different stages that form a continuous cycle. The main stages are:
1. Plan: Planning project requirements, features, and tasks.
2. Code: Writing and developing application source code.
3. Build: Converting source code into an executable application.
4. Test: Testing the application to identify and fix errors.
5. Release: Preparing the application for deployment.
6. Deploy: Deploying the application to the production environment.
7. Operate: Managing and maintaining the application.
8. Monitor: Monitoring application performance and identifying issues.
3. Principles of DevOps
The main principles of DevOps are:
* Collaboration: Development and operations teams work together.
* Automation: Repetitive tasks are automated to reduce manual effort.
* Continuous Integration (CI): Code changes are frequently integrated and tested.
* Continuous Delivery (CD): Software is continuously prepared for deployment.
* Continuous Monitoring: Application performance and system health are monitored.
* Continuous Improvement: Feedback is used to improve the development process.
4. DevOps Practices
The important DevOps practices include:
1. Version Control: Managing and tracking changes in source code.
2. Continuous Integration: Frequently integrating code changes and running automated tests.
3. Continuous Delivery/Deployment: Automating the software release and deployment process.
4. Infrastructure as Code (IaC): Managing infrastructure using configuration files.
5. Automated Testing: Testing applications automatically to identify errors.
6. Containerization: Packaging applications and dependencies into containers.
7. Monitoring and Logging: Tracking application performance and system activities.
5. Role and Responsibilities of a DevOps Engineer
A DevOps Engineer connects development and operations teams and ensures smooth software delivery.
The main responsibilities are:
* Develop and maintain CI/CD pipelines.
* Automate software building, testing, and deployment.
* Manage servers and cloud infrastructure.
* Configure and maintain development environments.
* Monitor application performance.
* Troubleshoot system and deployment issues.
* Ensure application security, reliability, and availability.
* Collaborate with developers and operations teams.
6. Skills Required for a DevOps Engineer
* Linux and operating system knowledge.
* Basic programming and scripting.
* Version control using Git.
* CI/CD pipeline management.
* Cloud computing knowledge.
* Containerization and orchestration.
* Monitoring and troubleshooting.
* Communication and collaboration skills.

Theory
a) What are Version Control Systems?
A Version Control System (VCS) is a tool that tracks changes in source code over time, enabling multiple people to collaborate efficiently.
It helps in:
* Storing different versions of code.
* Rolling back to earlier versions if needed.
* Managing contributions from multiple developers.
b) Types of Version Control Systems
1. Local VCS: Stores versions in a local database (e.g., RCS).
2. Centralized VCS (CVCS): A single server stores all versions, and clients check out files (e.g., SVN).
3. Distributed VCS (DVCS): Every developer has a complete copy of the repository (e.g., Git, Mercurial).
c) Popular VCS Tools for SCM
* Git: Widely used distributed version control system.
* Apache Subversion (SVN): Centralized version control system.
* Mercurial: Similar to Git but simpler command set.
* Perforce: Often used in game development and large binary file storage.

	e) Why is Git Preferred in DevOps?
* Distributed architecture enables faster collaboration.
* Lightweight branching and merging make feature development easier.
* Open-source and widely adopted in CI/CD pipelines.
* Offline capability allows work without constant internet.
* Integrates with GitHub, GitLab and Bitbucket.
f) Best Practices in VCS
* Commit frequently with clear messages.
* Use branches for new features or bug fixes.
* Pull the latest changes before starting new work.
* Avoid committing sensitive data.
* Keep repositories organized.
* Use meaningful commit messages.

Version Control Systems like Git are essential in modern software development for tracking changes, enabling collaboration, and ensuring code quality. 4. Theory
Jenkins is an open-source automation server used for Continuous Integration and Continuous Delivery (CI/CD). It helps developers automate tasks such as building, testing, and deploying software applications.
Continuous Integration (CI) is a software development practice in which developers frequently integrate their code changes into a shared repository. Each integration can trigger an automated build and testing process to identify errors early.
Working of Jenkins:
      1. Developers make changes to the source code.
      2. Code is stored in a version control system such as Git.
      3. Jenkins detects or receives the changes.
      4. Jenkins executes the configured build job.
      5. The build output is displayed in the console.
      6. Developers can verify whether the build was successful or failed.
Important Jenkins Components:
      * Jenkins Server: Manages build jobs and automation tasks.
      * Job: A task configured to perform a particular operation.
      * Build: An execution of a Jenkins job.
      * Workspace: Directory where Jenkins executes job commands.
      * Console Output: Displays logs and results of a build.
      * Plugins: Extend Jenkins functionality.

3. Theory
Docker is an open-source containerization platform used to develop, package and run applications in isolated environments called containers.
Docker allows applications and their dependencies to be packaged together, making them portable and consistent across different environments.
Docker Architecture
Docker follows a client-server architecture consisting of the following components:
1. Docker Client: It is the interface through which users communicate with Docker using commands such as docker run, docker pull and docker ps.
2. Docker Daemon: It is a background service responsible for managing Docker images, containers, networks and volumes.
3. Docker Images: Images are read-only templates used to create Docker containers.
4. Docker Containers: Containers are lightweight, isolated environments created from Docker images to run applications.
5. Docker Registry: It is a storage location used to store and distribute Docker images. Docker Hub is a popular public registry.
Docker Container Life Cycle
The Docker Container Life Cycle describes the different states of a container from creation to deletion.
The main stages are:
            1. Created: A container is created but not yet started.
            2. Running: The container is actively executing.
            3. Paused: The processes inside the container are temporarily suspended.
            4. Stopped: The container execution is stopped.
            5. Deleted: The container is permanently removed.
Docker provides commands such as docker run, docker stop, docker start and docker rm to manage the container life cycle.

1. What are Docker and Kubernetes?
Imagine you developed a small website that displays:
                  * Hello from Docker!
                  * This web application is running inside a Docker container.
You want to run this website reliably. Docker and Kubernetes help with different parts of that task.
Docker — runs the application in a container
Docker packages your application and its required files into an image. It can use that image to create and run containers.
Kubernetes — manages containers
Kubernetes helps run applications across a cluster, maintain the required number of copies, expose them through networking, and restart or replace failed Pods when possible.
Simple example: Docker helps run your website in a container. Kubernetes helps manage two or more copies of that website.
2. Important Kubernetes terminology
Learn these concepts in this order.
1. Docker image
An image is a packaged template containing the application files and instructions needed to run it.
Example: docker-webapp:latest
2. Kubernetes cluster
A cluster is a group of computing resources managed by Kubernetes. In our experiment, Minikube creates a local cluster on one computer.
3. Pod
A Pod is the smallest deployable unit in Kubernetes. It runs one or more containers. In our experiment, each Pod runs one Nginx container serving our website.
4. Deployment
A Deployment manages Pods and maintains the desired number of replicas. If we request two replicas, Kubernetes attempts to keep two Pods running.
5. Service
A Service provides a stable network endpoint for accessing the application Pods. Our experiment uses a NodePort Service.
3. How these components work together
Docker image
Contains the Nginx web application
Minikube cluster
Runs Kubernetes on your computer
Deployment
Requests two replicas
Pod 1
Nginx container
Pod 2
Nginx container
NodePort Service
Provides access to the application through a browser
For example, if one Pod fails, the Deployment can create a replacement to return to the desired number of replicas. The Service directs traffic to eligible Pods.
4. What are kubectl and Minikube?
                  * Minikube: Creates and runs a local Kubernetes cluster for learning and development.
                  * kubectl: The command-line tool used to communicate with Kubernetes and manage its resources.
                  * Docker: Builds images and runs containers. In this experiment, it also provides the driver for Minikube.
A cluster typically has a control plane, which manages the cluster, and worker nodes, which run application workloads. Minikube can run these roles together on one local node.
5. Theory you can write in your record
Kubernetes is an open-source container orchestration platform used to deploy, manage, and scale containerized applications. It automates container scheduling, scaling, service discovery, load balancing, and recovery of failed application Pods.
A Kubernetes cluster consists of a control plane and worker nodes. The control plane manages the cluster, while worker nodes run application workloads inside Pods.
The main components used in this experiment are:

1. Aim
To study and implement software configuration management and provisioning using Puppet manifests, modules, classes, and functions in Ubuntu Linux.
2. Theory
What is Puppet?
Puppet is a configuration management and provisioning tool used to automate the configuration of computers and servers.
Suppose you have 100 computers in a laboratory. You need to install software and create the same configuration on every computer. Doing this manually takes a lot of time.
Puppet helps automate this process by allowing you to write instructions in code.
For example, you can tell Puppet to:
                  * Install a software package such as curl.
                  * Create a file in a specific location.
                  * Write content into that file.
                  * Configure services and maintain the desired system state.
Important Puppet concepts
1. Manifest (.pp)
A manifest is a file containing Puppet instructions. It specifies the desired state of resources.
Example: site.pp tells Puppet to install curl and create a text file.
2. Module
A module organizes Puppet code into a standard directory structure so that configuration can be reused and maintained easily.
Example: a puppet_demo module stores its main class in manifests/init.pp.
3. Class
A class groups related resources into a reusable unit.
Example: demo_class creates a file and writes a message into it.
4. Function
A function performs an operation in Puppet code.
Example: notice('Hello') displays a message during Puppet catalog compilation.
How Puppet works
Puppet Manifest
Instructions written in a .pp file
Puppet Apply
Reads and processes the instructions
System Configuration
Installs packages or creates files
Verify the Result
Use cat or other commands to check
For this experiment, we use puppet apply to execute the manifests locally. This means you do not need a separate Puppet agent-server connection for these demonstrations, although you will check the Puppet server status as part of the initial setup.
